# 足球場邊記錄器 v5.120

手機場邊即時記錄足球比賽事件的單頁工具。

目前版本：**v5.120**

## v5.120 比賽時間改為整秒制

### 核心調整

使用者可見的比賽時間改為「整秒」基準。Epoch 欄位仍維持毫秒格式，但寫入時固定將毫秒尾數設為 `000`。

例如：

- 原本：`22:16:57.842` → 內部 epoch 尾數可能是 `842`
- v5.120：`22:16:57.000` → 內部 epoch 尾數固定為 `000`

因此畫面顯示 `22:16:57 → 22:17:03` 時，該段實際時間就會是 **6 秒**，可直接用畫面上的 HH:MM:SS 人工驗算。

### 改為整秒的時間

- 各比賽階段開始 / 結束
- 中場開始 / 結束 / 中場休息秒數
- 延長賽開始 / 結束
- PK 開始 / 結束
- 進行中主計時器與事件相對秒數

### 仍保留毫秒精度的系統時間戳

以下用途仍使用 `Date.now()`，不改成整秒：

- Match ID 的備援唯一值
- `_savedAt` / save timestamp
- Registry `updatedAt`

原因是這些欄位用於「資料唯一性、先後排序、判斷哪份資料較新」，同一秒內可能更新多次，因此需要毫秒精度。

### Safari 背景可靠性

本版 **沒有** 改成 `setInterval(() => seconds++)` 累加秒數。仍以系統時間差計算，因此 Safari 分頁進背景、鎖螢幕或被節流後，回到頁面仍可依時間差恢復正確秒數。

### 舊版進行中比賽

若從 v5.119 升級時仍有尚未完成的比賽，v5.120 會把該場的進行中時間邊界對齊整秒；已完成的歷史比賽則不改寫，避免發版後改變既有報表。

## v5.119 全場 PK 資訊去重複

### UI 調整

PK 完成後的「全場」結果畫面，原本會同時出現：

- 上方狀態列：`全場・PK 1:0`
- 比分區下方：`PK 1 : 0`

兩者屬於完全相同的資訊，因此 v5.119 改為：

- 上方狀態列只顯示 **「全場」**
- PK 比分只保留在主比分區下方的紫色 `PK x : x` 標籤
- 勝方徽章「勝」維持不變

這樣資訊層級更清楚：上方負責比賽階段／時間，比分區負責正規比分與 PK 結果，避免同一個 PK 比數在同一視窗出現兩次。

### 不影響

- PK 記錄流程
- PK 詳細輪次
- 摘要中的 PK 結果
- CSV 匯出
- 勝方判定
- 正規賽／延長賽比分

## v5.113 賽前「重設」按鈕辨識度提升

### 設計原則

「重設」是低頻率的 Secondary Action，因此不使用紅色，也不應搶過主要 CTA「開始比賽」；但它仍必須明確看得出可以點。

### 本次調整

- `↻` 與「重設」拆成獨立 icon / label。
- 按鈕改成較清楚的深藍透明底。
- 使用淡藍灰描邊。
- `↻` 圖示使用較亮的淺藍色。
- 可視高度約 33–34px。
- 透過透明 pseudo hit-area，實際可點範圍約 44px。
- 保留賽前狀態列右側位置。
- 不使用紅色，避免被理解為危險 / 刪除主操作。

### 狀態感知

只有賽前真的存在可清除資料時才顯示並啟用「重設」。

沒有任何可重設資料時：

- 不顯示
- `disabled=true`
- `aria-hidden=true`
- 不進入鍵盤 tab 順序

### 確認訊息

按下後仍保留二次確認，並明確說明會清除：

- 賽事名稱
- 場地
- 對手
- 名單
- 守門員
- 比賽時間
- 其他賽前設定

### Recovery 何時才出現

Recovery 能力仍保留在程式底層，但只有真正發生：

才會啟動。

1. 不把空白資料寫回遺失的 Match ID

### 產品定位

- URL Match ID：正常比賽身分
- localStorage：正式比賽資料
- Match Registry / Recovery：低頻災難復原

Recovery 不再是日常操作功能。

這代表約 19 小時 8 分鐘。問題不是資料計時錯誤，而是原本 LIVE 列是針對短時間字串設計；長字串會向左擠壓置中的「比賽中」與 LIVE 標籤，造成重疊。

### v5.92 處理

1. 主計時：
   - `< 1 小時`：`MM:SS`
   - `≥ 1 小時`：`H:MM:SS`
   - 例如 `1148:15` 會顯示為 `19:08:15`

2. 長時間版面：
   - 1 小時以上，LIVE 列自動切成真正三欄 Grid：
     `LIVE | 比賽中 | 時間`
   - 不再使用會與長時間重疊的絕對置中排版
   - 長時間自動縮小時間字級
   - 100 小時以上再進一步縮字

3. 超時提示：
   - `< 1 小時`：`超時 +28:15`
   - `≥ 1 小時`：`超時 +18:48:15`
   - 長超時 badge 自動縮字與限制寬度

4. 數字穩定：
   - 主計時與超時提示使用 `tabular-nums`
   - 秒數跳動時每個數字維持等寬，降低版面晃動

5. 異常長時間提醒：
   - 單一比賽段落超過 3 小時後，重新開啟頁面或從背景回到前景時提示一次
   - 選擇「繼續計時」：本段不再重複提示
   - 選擇「結束比賽」：進入既有的正常結束流程
   - 程式不會擅自自動停止比賽

6. 原始資料不截斷：
   - LocalStorage 仍保存完整 timestamp / 秒數
   - 只調整顯示格式與防爆排版
   - 比分、事件、Match ID、Recovery、摘要與 CSV 資料邏輯不變

## v5.91 歷史：主計時與超時提示秒數同步修正

### 問題現象

比賽進行中的主計時例如顯示：

`1148:15`

但下方規定時間提示可能暫時顯示：

`超時 +1128:14`

兩者會差 1 秒。

### 根因

兩個畫面原本不是由同一個更新時脈驅動：

- 主計時器：`requestAnimationFrame(tick)` 持續更新
- 規定時間 / 超時提示：`setInterval(renderRegulationTimeAlert, 1000)` 每秒獨立更新

當主計時器剛跨到下一秒，而 1 秒 interval 尚未執行下一次時，就會短暫出現「主計時已 +1 秒、超時提示仍停在上一秒」的情況。

這不是規定時間的減法公式錯誤，而是兩個 UI 使用不同更新排程造成的顯示不同步。

### v5.91 修正

- `tick()` 每一幀只取得一次 `timerSec`
- 同一份 `timerSec` 同時交給：
  - 主計時器
  - `renderRegulationTimeAlert(timerSec)`
- 超時秒數與主計時統一使用同一個 `Math.floor()` 整數秒基準
- 移除原本獨立的 `setInterval(renderRegulationTimeAlert, 1000)`

因此若規定時間為 20:00：

`主計時 1148:15 → 超時 +1128:15`

兩者會使用相同秒數基準，不再固定落後 1 秒。

## v5.90 歷史：Recovery 流程修正與降級

### 取消啟動時自動彈出

v5.89 使用乾淨網址進入時，只要 Registry 偵測到未完成比賽，就會自動顯示「發現尚未完成的比賽」。

v5.90 改為：

- 正常開啟根網址：直接建立新的 URL Match ID
- 開啟既有 `#match=...`：直接恢復該場
- 不再自動出現 Recovery Modal
- Recovery 能力保留，但改放在「這是什麼？」內的次要入口
- 沒有可復原比賽時，該入口完全不顯示

### 修正「繼續這場比賽」無法載入

v5.89 先把全域 `KEY` 切到目標比賽，再執行 `location.reload()`。
reload 期間的 `pagehide / visibilitychange` 又會自動執行 `saveState()`，因此有機會把目前畫面的 state 寫進目標比賽 key。

v5.90 改為：

1. 先保存目前場次
2. 不切換目前 `KEY`
3. 只更新 URL `#match=目標ID`
4. reload 後由啟動流程重新解析 Match ID
5. reload 切換期間暫停 background autosave

因此不會再用目前 state 覆蓋要找回的比賽。

### 修正舊比賽全部顯示相同更新時間

v5.89 的 `inferSavedUpdatedAt()` 最低值錯誤使用接近 `Date.now()`，造成掃描舊資料時多筆場次看起來都是「剛剛更新」。

v5.90：

- `saveState()` 寫入 `_savedAt`
- 舊資料依 start/end/period/marker 的真實 timestamp 推算
- Match Registry 每次啟動都由真正的 match state 重建
- Registry 只作索引，不是比賽本體

### 使用原則

平常完全不需要操作 Recovery：

- `#match=A` 就是比賽 A
- `#match=B` 就是比賽 B
- Safari 背景重載時依 URL Match ID 找回原場
- 只有真的需要找回過去未完成場次時，才從「這是什麼？」進入資料復原

- 更舊的 `football_marker_v218` 也會被加入復原清單。

## v5.87 歷史：多分頁比賽 Session 獨立化

### 問題原因

v5.86 以前整場比賽資料固定使用：

`localStorage["football_marker_v218"]`

瀏覽器的 `localStorage` 是同一網站來源（Origin）下所有分頁共用，因此不同 Safari / Chrome 分頁會讀寫同一場比賽。背景分頁若被行動瀏覽器重新載入，也會再次讀到另一分頁最後寫入的資料，看起來就像兩個分頁完全同步。

### v5.87 解法

本版改成：

- 每個分頁由 `sessionStorage` 取得一個獨立 `Match Session ID`
- 真正的比賽資料仍寫入 `localStorage`
- 但 key 改為：

`football_marker_v218_session_<Session ID>`

因此：

- 分頁 A 與分頁 B 的比分、事件、計時互不影響
- 同一分頁重新整理後仍會讀回自己的 Session
- 同一分頁在比賽中切到背景再回來，不會讀到另一分頁的比賽
- 我方常用隊名、最近場地、學習背號、上次名單等「使用者偏好」仍維持跨分頁共用

### 舊版資料遷移

第一次由 v5.86 升級到 v5.87 時：

- 第一個開啟的 v5.87 分頁會承接一次舊 `football_marker_v218` 比賽資料
- 之後新分頁會建立自己的獨立 Session
- 舊 key 不會被刪除，避免升級過程造成資料遺失

### 注意

「＋ 新比賽」仍表示清空**目前這個分頁 Session**並建立下一場；不會清除其他分頁正在記錄的比賽。

## v5.05 全場「＋ 新比賽」Safari 遮擋根因修正

### 這次確認到真正原因
前幾版一直增加 `fullTimeBottomSpacer`，但實際上：

```css
.finalToolsCard {
  position: fixed;
}
```

而 `＋ 新比賽` 位於 `.finalToolsCard` 裡面。

因此即使按鈕後面增加 200～300px 的 spacer，
**fixed 工具卡仍固定貼著 Safari viewport 底部**，
spacer 根本無法把按鈕往上推。

- 不用 fixed 新比賽按鈕

- 開始比賽、開始下半場及開始延長賽後，自動將事件操作區捲動至 Safari 工具列上方。
- 比賽結束或 PK 結束後，自動將賽後輸出按鈕帶到安全可見位置。
- 增加 iPhone Safari 底部安全捲動空間，避免事件紀錄及賽後按鈕被工具列遮住。
- 我方隊伍名稱的藍色輸入狀態僅限賽前；開賽後各狀態均改為純文字顯示。
